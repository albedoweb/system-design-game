# Image Atlas

Image Atlas is a global photo service. One million users upload, search by user or one tag, and open image details from three regions. You design the serving path, metadata stores, replicas and caches. The original image store is a fixed global provider you cannot replace.

The model is a teaching simulation, not a production benchmark. All prices and coefficients are conditional in-game values.

For a player-oriented walkthrough with quick fixes, result reading and experiments, see [the Image Atlas player guide](image-atlas.html).

## Fixed endpoints

There are exactly six fixed nodes:

- `client-na`, `client-eu`, `client-ap`: regional demand populations. Each fixed Client node has a shared population aggregate link with **100 Gbit/s in each direction** (separate RX and TX capacity) and a 20 ms regional RTT.
- `blob-na`, `blob-eu`, `blob-ap`: regional endpoints of the mandatory global blob provider.

Each **business request / end-user** separately has a **1 Gbit/s access link** shared by all of its child transfers, especially the ten search thumbnails. The 1 Gbit/s per-request cap is not the regional client capacity. Client traffic is charged on the aggregate path as well as the per-request access link.

You may rename and move fixed nodes. You cannot change their kind, region or configuration, add another client/provider, or replace the provider with a player-owned blob store. The same rule is enforced by the graph validator and the backend.

The provider keeps originals durable globally. Its internal replication is included in the provider price and is not a player-owned copy. Thumbnails are generated by the provider as variant reads; they are not allocated as 384 TB of player storage in advance. The global 6 PB original base is counted once, not once per regional endpoint.

## Regions and links

Demand is split equally across North America (`na`), Europe (`eu`) and Asia Pacific (`ap`).

- Local propagation is 1 ms one-way.
- Inter-region links form a full mesh. Each direction of each pair has its own **100 Gbit/s one-way channel**; the two directions are not pooled into 200 Gbit/s. Latencies: `na-eu` 40 ms one-way, `eu-ap` 70 ms, `na-ap` 80 ms.
- Every transfer using a region pair shares that pair's channel in that direction. Drawing a second arrow does not create a second cable.
- Each physical instance has **10 Gbit/s in each direction** (separate RX and TX limits), not a single pooled 20 Gbit/s allowance.
- One explicit path is used per transfer. Parallel logical arrows never multiply capacity.

A client may use an app in another region. That is legal but the cross-region transfer is charged and its latency is modelled.

## Node kinds

| Kind | What it is | Editable configuration |
| --- | --- | --- |
| Client | Fixed regional demand population | Label, position |
| App | Player compute pool | Instances, delivery, buffering, retries, retry backoff |
| Metadata | Durable indexed metadata origin/replica | Backend, index mode, disk per instance, instances, replicas, resident cache |
| Cache | Byte-bounded LRU cache | Medium, instances, capacity, fill policy, SSD disk tier |
| Blob | Fixed global provider endpoint | Label, position |

Every physical compute instance has 8 cores, 24 GB RAM (22 GB usable after 2 GB base RSS), a 10 Gbit/s NIC in each direction, 500 MB/s disk, 20k IOPS and a 2 TB disk. The 2 TB disk is included in the instance price; 8 TB and 16 TB are incremental tiers.

A pool spreads work over its physical instances. A single-instance failure removes one instance, not the whole pool, and never multiplies the surviving resources.

## Edges and routes

There are four operations:

- `traffic`: client to app. A client may have several explicit traffic edges as failover choices.
- `metadata`: app to metadata. Selects the store for that app’s reads and new immutable uploads.
- `blob`: client to provider (direct delivery), app to provider or cache (proxy delivery), or cache to provider.
- `replicate`: metadata origin to a metadata recipient.

Other combinations are rejected. Self loops, duplicate ids, duplicate `(source, target, operation)` tuples, dangling endpoints and non-replicate cycles are errors.

### Client failover

A client may list several connected apps. After 250 ms failure detection, the routing service selects the lowest-latency healthy **connected** app. It never follows an implicit edge that is absent from the graph. If no connected healthy app exists, offered demand fails; it is not silently dropped. A region outage does not remove users or offered traffic.

### App delivery

An app is either `direct` or `proxy`.

- **Direct**: clients fetch image bytes straight from a provider endpoint. The direct app has no blob edge. A direct client may list one or more explicit provider endpoint edges; the nearest healthy connected endpoint is selected. The app still serves control and metadata traffic.
- **Proxy**: the app carries image bytes. It has exactly one data path:
  - directly to one provider, or
  - to exactly one cache, and that cache has exactly one edge to one provider.

Clients using only proxy apps have no blob edge of their own. A cache serves real bytes on a hit and fills from the provider on a miss. A cache response still uses the client link; a cache hit saves provider retrieval and fill traffic, not the client transfer. A cache is never durable storage.

`streaming` proxy mode keeps a 64 KB buffer per active hop. `buffered` proxy mode retains the payload in memory. App retries are 0 to 2 with a fixed bounded backoff and an idempotency key, so a retry cannot create a second image or metadata record.

### Metadata origins, replicas and retries

Each app has exactly one metadata edge. That store serves the app’s reads and accepts new immutable uploads as an **origin**. Every metadata store attached to an app is an origin and may also be a replica. A regional store can therefore hold both writer and replica roles.

Metadata records are append-only entries keyed by a globally unique upload/idempotency id. Replicas receive **direct per-origin logs** and maintain origin-specific progress and dedupe. There is no single global home writer and no single global watermark.

- Same id and same content has one business effect.
- Same id with different content is rejected.
- Before the first payload transmission the routing service binds an upload id to its chosen healthy origin.
- All retries reuse that origin and its durable object key.
- While the owner is unavailable the id stays unknown/pending and must never append at another origin. Only a distinct new upload id may choose a different origin.
- A lost ACK is unknown/pending until the original outcome is available. It does not undo a commit and does not trigger a second effect.
- ACK requires the object durable commit and the configured local durable metadata copies. Global search publication is a separate, later event.

Replicate edges are direct origin-to-recipient logs. A full-mesh directed regional topology is the simplest complete distribution. Cycles consisting only of replicate edges are allowed and deduped by origin/sequence: a recipient applies each origin record once and never recursively rebroadcasts applied records. `A → B` and `B → C` do not imply `A → C` in v1. Missing replicate edges are valid-but-incomplete distribution and can fail runtime freshness; they are not rejected at import.

### Metadata sharding and capacity

Metadata is sharded. For each metadata node:

```
shardCount = floor(instances / replicas)
instances must be divisible by replicas
logical capacity = shardCount × diskTb
```

Every physical copy consumes provisioned and billed disk. Capacity must provision a complete regional metadata dataset and all physical copies for every player metadata store; it is not reduced to bytes that a particular graph happened to deliver. Workload bytes are not multiplied by copy count twice, but storage copies are real.

Index modes:

| Mode | Extra bytes per image | What it can serve |
| --- | ---: | --- |
| `none` | 0 B | Point lookups by key only. Search by user or tag is rejected with `metadata_index_missing`; the engine does not simulate a table scan. |
| `user` | 64 B | Recent search by user. Tag search is still rejected. |
| `user-tag` | 352 B | Recent search by user and by one tag: 64 B user entry plus three 96 B tag postings. |

These are disclosed teaching assumptions, not measured database overheads. They are also an engine rule, not a claim that a real SQL database cannot scan. Metadata writes and replication pay the selected index amplification.

Metadata resident pages are bounded by the per-instance resident cache. The rest of the metadata is read from disk. The whole dataset never has to fit in RAM, and it is never materialised as billions of JavaScript rows.

Every scenario starts with replicas caught up to the mature synthetic dataset. No general consensus, leader election or Byzantine protocol is simulated.

## Capacity at day 30

The mature dataset is evaluated at day 30:

- 1M users × 50 uploads/day × 30 days = 1.5B images.
- Originals: 1.5B × 4 MB = 6 PB.
- Metadata: 1.5B × 8 KB = 12 TB before indexes.
- Thumbnails: 384 TB if every image had a pre-materialised 256 KB thumbnail. They are variant reads, not player storage.

The provider original bill is fixed at 6 PB × $6/TB-month = $36,000/month. It is shown separately from your controllable spend.

Metadata capacity is checked per node using logical capacity. The estimate also reports physical copies and provisioned disk. Cache capacity must fit the per-instance RAM limit (22 GB) or the declared SSD tier. A cache node’s `capacityGb` is total pool capacity; per-instance share is `capacityGb / instances`. RAM is included in instance compute price and is never billed again.

A partial or semantically invalid graph still receives a capacity estimate and a list of validation problems. Capacity estimation never crashes the editor.

## Workload

Daily-average rates:

- Uploads: 50M/day, 578.7/s average.
- Searches: 50M/day, 578.7/s average.
- Detail clicks: 2 per search = 100M/day, 1,157.4/s average.

Each search returns ten results, and each result record is 8 KB. Search thumbnails are 10 × 256 KB. Detail opens one 4 MB original and an 8 KB metadata record. Upload carries one 4 MB original and 8 KB of metadata.

Popularity is seeded independently of the graph: 80% of read demand goes to the 10,000 hottest keys and 20% to a representative 1M-key long tail mapped onto the full mature dataset. The mapping does not shrink provisioned storage or per-operation work. The same seed and versions reproduce the same trace; node ids and insertion order never influence random draws.

A cache starts empty and is filled by warm-up demand. There is no arbitrary hit percentage.

Qualification scenarios:

| Case | Demand | Fault |
| --- | --- | --- |
| Normal | Daily average | None |
| Peak | 2× average | None |
| Node failure | 2× average | One physical instance per player pool, 20–40 s |
| Link failure | 2× average | `na-eu` both directions, 20–40 s |
| North America outage | 2× average | NA datacenter resources and provider endpoint, 20–40 s |
| Europe outage | 2× average | EU datacenter resources and provider endpoint, 20–40 s |
| Asia Pacific outage | 2× average | AP datacenter resources and provider endpoint, 20–40 s |

Every case uses 20 s warm-up, 60 s measured traffic and up to 10 s **request drain**. Request drain is separate from the **no-new-offers consistency postlude**, which runs through the last committed ACK + 120 s and checks publication of every committed upload, including lost-ACK commits. Background work and cost remain counted but are excluded from measured-window load averages. A fault is followed by 20 s recovery. Each region is tested separately at every replay seed. Seeds101/211/307 are additional calibration replays. Link outage is `na-eu`. The v1 node case is explicitly named **one instance per pool**.

Region outage still offers client demand and counts it in the denominator, so failures cannot be hidden by removing users. Fixed injected interruptions do not destroy every disk.

One in a hundred business detail requests is a **recent-read probe** for an upload offered 20–2000 uploads earlier. It stays a normal business request: it is counted in detail availability and latency. It may be served by the local replica, or fall back to the origin store and the origin provider endpoint while the record is younger than the 60 s remote-visibility window.

Freshness is a **consistency assertion**, not a second availability gate. A recent read that fails during an outage is counted as a failed business response; it is not by itself a freshness violation. The freshness gate needs at least one observed assertion, no successful stale/missing/wrong response, and a visibility lag within 120 s. Synthetic old keys have full regional visibility at the start. The consistency postlude checks every durable commit, including commits whose ACK was lost.

## Targets

Normal and peak, p99.9 over successful responses:

| Operation | Normal/peak | Incident |
| --- | ---: | ---: |
| Detail | 300 ms | 600 ms |
| Search | 250 ms | 800 ms |
| Upload | 1,000 ms | 2,000 ms |

- Availability: at least 99.5% for each operation in normal/peak.
- Detail's normal/peak target is **300 ms p99.9**, a disclosed game adaptation of Google's original 200 ms requirement. The 200 ms figure remains attributed to Google; the game adds 1% causal recent detail reads across three regions while the fixed blob provider only exposes a new object remotely after 60 s. A correct cross-region origin GET pays 160 ms round-trip propagation + 35 ms minimum service start + 32 ms payload = 227 ms before app/metadata/client overhead, so increasing CPU or RAM cannot meet 200 ms. Every business read, including probes, stays in the denominator; no other target, price, workload or fault changed.
- Incident availability: at least 98% for each operation across the incident case and the fault window.
- Recovery: final 10 s availability at least 99.5%, with the applicable incident latency bound.
- Hard deadlines: detail 2 s, search 3 s, upload 5 s.
- No acknowledged data loss, no duplicate effects and no missing successful search results.
- p99.9 requires at least 10,000 successful samples per operation per case. If a run is too short, the duration extends deterministically. A sample count is always shown.

Availability uses every offered request. Rejected, timed out, incorrect, stale and missing-data responses are failures. Successful percentiles are shown separately so a high latency cannot be hidden by a low availability.

The API does not accept a pass just because the result says `passed: true`. It rechecks the returned availability, p99.9 latency and sample counts against these frozen targets, requires the per-operation `availability:<operation>` and `p999:<operation>` evidence gates, and checks freshness, integrity, publication and incident/recovery windows. Freshness probes are consistency assertions, not a demand that every recent business request succeeds: a timed-out read during a temporary outage counts against availability, not automatically against freshness, as long as no successful stale or incorrect response was returned and every committed record publishes within 120 s.

A scenario subset is an **exploratory** run. Qualification requires all seven cases at the selected replay seed, including a separate outage of each region. Calibration repeats qualification with additional seeds. An event or memory limit produces an incomplete result, never a pass.

## Cost

Conditional monthly prices:

- Compute: $0.20 per instance-hour, 730 hours/month; includes 8 cores, 24 GB RAM and 2 TB disk.
- Extra disk above 2 TB: $6/TB-month.
- Provider originals: $6/TB-month, 6 PB fixed base.
- Client egress: $0.006/GB.
- Provider retrieval: $0.002/GB.
- Cross-region player transfer: $0.01/GB.
- API: $0.0000004 per read and $0.000005 per write.
- Budget: $205,000/month.

The monthly estimate uses normal daily demand × 30 days. Incident replay cost is reported separately and is never extrapolated across 30 days. The fixed provider base and your controllable subtotal are shown separately. Metadata replicas and caches are charged explicitly. Cache and metadata RAM are part of compute and are not billed a second time.

Traffic and API lines are measured from the normal replay: client egress on returned bytes, provider retrieval on bytes actually read from the provider, cross-region on bytes that cross a private region pair, and **API fees per admitted provider RPC** (a ten-thumbnail search fan-out is ten reads; retries are charged too). Failed and partial transfers keep the bytes they really moved.

The budget has been checked against two independent design families on the same traces and five seeds in development. It remains an in-game target; the reference candidates are teaching examples, not promised passing designs, and any graph still has to qualify on all seven cases at its chosen seed.

## Model assumptions and coefficients (work model v1)

These are disclosed teaching assumptions, not vendor benchmarks. They are the only coefficients the evaluator uses.

- **CPU**: core-milliseconds of work. An app request costs 0.25 ms parse plus 0.35/0.5/0.9 ms for detail/search/upload handling. A metadata point lookup costs 0.2 ms, a user index 0.35 ms, a tag index 0.45 ms plus 200 posting reads. A durable local metadata copy costs 0.08 ms CPU and 4 IO operations (the durable append itself is charged as disk IO, not double-counted as CPU).
- **Disk**: each instance exposes 4 IO lanes sharing 500 MB/s and 20 000 IOPS, so one lane is 125 MB/s and 5 000 IOPS. A task holds one lane for the slower of its byte and IOPS work.
- **Network**: every flow owns one 1 Gbit/s lane on each physical resource of its explicit path. A 10 Gbit/s instance NIC exposes 10 one-way lanes in each direction; a relayed duplex flow holds one lane in each direction. A 100 Gbit/s shared link or provider endpoint exposes 100 lanes per direction and a one-way flow holds 1 lane. RX and TX are separate; they are never pooled. Parallel arrows never add capacity.
- **Streaming vs buffered**: a streaming proxy pipeline reserves every hop at once and pays one serialization of the payload. Buffered forwarding stores and forwards: one serialization per hop plus a full payload buffer. A relay holds a small fraction of a core and of an IO lane, never a whole core per flow.
- **Propagation**: geographic delay is a separate stage after serialization. It holds no bandwidth. A fault during propagation still loses the response and the bytes already serialized stay billed.
- **Search fan-out**: the ten thumbnail children share the 1 Gbit/s end-user access link. With a cache, the client stage carries all ten results while the provider stage fetches and pays only the misses; the client stage cannot finish before those bytes exist. Coalesced fills make the second reader wait for the real fill; a failed fill wakes the waiter for a retry.
- **Provider**: the 10 000 read/s and 2 000 write/s quotas are admission rates, separate from the service-start bands. Payload serialization is charged on the provider endpoint lanes as well.
- **Metadata protocol**: immutable per-origin records; write quorum W = floor(replicas/2)+1 and read quorum R = replicas−W+1 over actual copies. With three copies one instance loss is survivable; two copies cannot commit after a loss. Replication is direct per-origin, pipelined, and never rebroadcasts applied records. New uploads use their own key namespace, so a new object can never alias a cached old image.
- **Transport approximation**: fixed lane reservation, not TCP or ideal fair sharing. The scheduler uses one FIFO per physical resource; a task that needs several queues can be held behind another task's head, so very wide multi-hop proxy paths can show queueing even when each resource has spare average capacity. This is a disclosed limitation of the shared resource kernel, not a hidden penalty or bonus.

Make one change, then read what the model did

Quick start

A useful loop is short: read the task, clear validation, run once, then compare one deliberate change.

  1. Read the Task brief once. It states the workload, the latency and availability targets, the budget, and the seven required cases.
  2. Clear blockers before running. Open Issues in the inspector and fix errors first. Warnings explain pressure; they do not always block a run.
  3. Keep the Seed fixed for comparisons. The same seed and the same model reproduce the same demand and fault trace. Change one graph setting at a time.
  4. Run the evaluation. A full qualification run evaluates all seven cases. A scenario subset is exploratory and cannot qualify.
  5. Open Results & telemetry. Choose a case tab, read Gates, then Operations.
  6. Compare the same case after the change. If the change helped one metric but hurt another, you have found the trade-off — not yet a fix.

Before a big experiment, Export

Nothing is saved automatically. Export writes the graph, node settings, positions and seed to a file. Import opens such a file later. Reset or a page reload starts again from the starter graph with the default seed and no previous result. A saved file is never deleted by Reset.

Two common confusions

“I store metadata, but search still fails.”

Storing a metadata record and being able to search it are different things. The record can be durable while the store still has no index that can answer the query. In this simulation, search does not silently fall back to a table scan: if the declared index cannot serve the query, the request fails with metadata_index_missing.

  1. Select the metadata store on the canvas.
  2. In the Inspector, find Index mode.
  3. For both user searches and one-tag searches, choose User + tag index (352 B/object).
  4. If you only need search by user, User recency index (64 B/object) is enough.
  5. Then check capacity separately: the index also consumes disk on every physical copy.

Why this is a game rule, not a database claim. Real SQL databases can scan a table. This model deliberately does not simulate that scan. The index choice is a disclosed teaching rule about the cost of keeping search cheap and predictable.

“Upload takes 3.4 s, but the provider endpoints are regional.”

The 3.4 s in this section is an illustrative example, not a diagnosis of your graph or a measured result from your run.

A 4 MB original sent over one 1 Gbit/s lane takes about 32 ms to serialize:

4,000,000 bytes × 8 ÷ 1,000,000,000 bit/s = 0.032 s

On top of that, the provider charges a write service-start delay of 80, 140 or 200 ms (plus 4 ms of durable service), then the upload needs its metadata durable commit and the normal network and queueing stages. Best case is roughly 116 ms before propagation, metadata work and queues — far below 3.4 s.

A regional provider endpoint removes the long geographic propagation only when the path stays local. It does not remove provider admission limits, the shared regional link, instance NIC or disk queues, the metadata commit, or the cost of retries. Those are usually where a multi-second tail comes from.

Streaming proxy mode pays one payload serialization across overlapping hops. Buffered mode pays one serialization per hop and keeps the whole payload in memory. Even three buffered hops add only about 96 ms of serialization, so 3.4 s still points at waiting or repeated work, not at the speed of light between regions.

How the three requests travel

Every request starts at a fixed regional Client population. Each business request has its own 1 Gbit/s access link, shared by all of its child transfers. The Client node also has a shared population link of 100 Gbit/s in each direction. The two limits are separate.

Upload

One original, one metadata record

  1. The client sends the request to a connected app.
  2. The app handles control work and binds the upload to one metadata origin.
  3. The 4 MB original goes to a provider endpoint. In direct delivery the client sends it to the provider; in proxy delivery the app carries the bytes.
  4. After the payload, the provider starts its durable write, then the metadata store commits the record and the required local copies. The ACK waits for the object durability and that local metadata quorum. It does not wait for cross-region replication or global search publication; those are separate, later events.
  5. The client receives the acknowledgement.

Search

One index lookup, ten thumbnails

  1. The client sends the search to an app.
  2. The app asks its metadata store for the ten most recent matches. The declared index must serve that query.
  3. The ten 256 KB thumbnails are fetched from the provider, or from one cache on a hit.
  4. The children are fetched concurrently on the server side, but the ten thumbnails share the request’s 1 Gbit/s client access link, so they serialize there.
  5. Search completes only when the required children complete.

Detail

Point lookup, then one original

  1. The client sends the detail request to an app.
  2. The app performs a point lookup in its metadata store and returns the 8 KB record.
  3. The 4 MB original is fetched from the provider, directly or through the proxy path, or from a cache on a hit.
  4. A cache response still uses the client link. A hit saves provider retrieval and fill traffic, not the client transfer.

Edges describe intent; physical channels carry the bytes

A logical arrow on the canvas is not its own cable. Every transfer using a region pair shares that pair’s channel. Parallel arrows never add capacity. One explicit path is used per transfer.

The four edge operations. Other combinations, self loops, duplicate tuples and non-replicate cycles are rejected.
Operation Allowed endpoints What it means
Traffic Client → app Business requests and responses. Several explicit traffic edges can list failover apps; routing still needs a healthy connected path.
Metadata App → metadata store The app’s reads and new immutable uploads. An app has exactly one metadata edge, and that store becomes an origin for its uploads.
Blob Client → provider; app → provider or cache; cache → provider Image bytes. Direct clients read from explicit provider endpoints; proxy apps carry bytes to one provider, or through one cache that points at one provider.
Replicate Metadata origin → metadata recipient A direct per-origin log. Cycles of replicate edges are allowed and deduplicated by origin and sequence; records are not rebroadcast transitively.

Fixed pieces and your pieces

There are exactly three regional Client populations and three regional provider endpoints. You cannot add another Client or provider, or replace the provider with your own blob store.

Global blob provider Fixed regional endpoints for the mandatory original store. Each endpoint has 100 Gbit/s each direction, 10,000 read RPC/s and 2,000 write RPC/s. Label and position only

A physical instance has 8 cores, 24 GB RAM (22 GB usable), a 10 Gbit/s NIC in each direction, a 500 MB/s and 20,000 IOPS disk, and a 2 TB disk included in its price. A pool spreads work across instances. One instance failure removes one instance, not the whole pool.

Canvas position is not routing

Dragging a node changes only its position in the diagram. It does not change the node’s Region or the request path. Player apps, metadata stores and caches have an editable Region in the Inspector; fixed Client and provider endpoints do not. To use a nearer provider, connect an existing regional provider endpoint — do not drag the fixed provider and expect the routing to follow.

Choices and trade-offs

There is no single “correct” setting. Each choice moves work, bytes, cost or risk somewhere else.

Direct or proxy delivery

Direct: clients fetch image bytes straight from a provider endpoint. The app handles control and metadata but does not carry the original bytes. Direct apps have no blob edge; clients need explicit provider endpoint edges.

Proxy: the app carries image bytes to one provider, or through exactly one cache that points at one provider. This enables caching and keeps bytes on your path, but spends app NIC, CPU and buffer memory.

Trade-off: direct removes app bandwidth cost; proxy adds a place to cache and observe, but adds a relay that can queue.

Streaming or buffered proxy

Streaming keeps a 64 KB buffer per active hop and reserves the hops together, paying one serialization of the payload.

Buffered stores and forwards: one serialization per hop plus a full payload buffer in RAM.

Trade-off: buffered can reach the hard memory limit sooner and adds serialization. Streaming is lighter, but the path still shares queues.

Add a cache

A cache is a finite byte-bounded LRU store. RAM capacity is limited to 22 GB per instance; SSD capacity is bounded by the declared disk tier. The pool capacity is divided across instances.

Coalesce makes one provider fill per key when several readers miss together. Independent lets each miss fill separately.

Trade-off: a hit saves provider retrieval and fill traffic, not the client transfer. A cache starts empty, cannot accelerate a fresh write, and is not durable storage. Coalescing protects the provider but makes the second reader wait for the real fill.

Retries and backoff

Retries are bounded from 0 to 2 with a fixed backoff. An upload retry reuses the same upload id and origin, so it cannot create a second image or metadata record.

Trade-off: a retry can turn a transient failure into a success, but it pays the transferred bytes again and adds load. It does not fix a missing index, an undersized store, a bad route, or a provider that is genuinely unavailable.

Replicas and regions

A metadata store can hold both writer and replica roles. Replicate edges are direct per-origin logs. A → B and B → C do not imply A → C.

Trade-off: more copies and more regions improve failure tolerance and locality, but consume disk, write work and budget. A missing replicate edge is valid but incomplete, and can fail freshness at runtime.

Failover edges

A client may list several connected apps. After 250 ms failure detection, routing selects the lowest-latency healthy connected app. It never follows an edge that is absent from the graph.

Trade-off: failover needs real capacity on the other side. Adding an arrow does not duplicate compute, metadata or cache resources.

Metadata, indexes and search

Search is deliberately narrow

Search is by user or by one tag, returns the ten most recent matches, and has no general text search. The index mode must match the query:

Index bytes are per image. The totals below are per complete dataset; every physical copy repeats them.
Index mode Extra bytes per image What it can serve
None 0 B Point lookups by key only. Both user search and tag search are rejected with metadata_index_missing.
User 64 B Recent search by user. Tag search is still rejected.
User + tag 352 B Recent search by user and by one tag: 64 B for the user entry plus three 96 B tag postings.

At 1.5 billion images, the base 8 KB record is about 12 TB per complete regional dataset. A user index adds about 96 GB (0.096 TB) and a user-tag index adds about 528 GB (0.528 TB) before physical copies, so user-tag is roughly 12.528 TB of logical data per dataset. Copies multiply the physical requirement.

SQL or KV?

Both backends are durable and both use the declared index mode. In this version they have the same capacity and work coefficients; there is no hidden “SQL is faster” or “KV magically searches everything” bonus. The KV description is key-addressed, so it has no free general search — but neither does SQL without the matching index. Do not expect a backend switch to repair a missing index.

Shards, replicas and capacity

For each metadata node:

shardCount = floor(instances ÷ replicas)
instances must be divisible by replicas
logical capacity = shardCount × diskTb

Example: 6 instances, 3 replicas and 8 TB per instance give 2 shards × 8 TB = 16 TB of logical capacity. That is also 48 TB of provisioned disk (6 × 8 TB), and the 16 TB dataset copied three times is 48 TB of physical copies. Capacity provisions the complete regional dataset and every physical copy, not only the bytes a particular graph delivered.

Writes, replicas and retries

Records are immutable append-only entries keyed by a globally unique upload id. An upload binds to one healthy origin before the first payload byte and all retries reuse that origin. Same id with same content has one business effect; same id with different content is rejected. While the owner is unavailable, the id stays pending and must not append at another origin.

Write quorum is floor(replicas ÷ 2) + 1; read quorum is replicas − write + 1. With three copies, one instance loss is survivable. With two copies, a loss prevents a write quorum. More copies mean more disk and write work.

Publication and freshness

An acknowledgement means the object is durable and the configured local metadata copies are committed. It does not wait for cross-region replication or global search publication; those are separate, later events. The provider exposes a new object to remote reads after 60 s; an origin read sees the writer’s upload immediately. A recent read that cannot see the record may fall back to the origin while the record is younger than that window.

Freshness is an assertion about successful recent reads, not a second availability gate. A timed-out read during an outage counts against availability; it is not automatically a freshness violation. A successful stale, missing or incorrect response is a freshness problem.

Disk tiers change capacity, not disk speed. Every instance keeps 500 MB/s and 20,000 IOPS regardless of whether you choose 2 TB, 8 TB or 16 TB. If metadata IO is the bottleneck, more TB will not help; use more instances, resident pages or a different index/query trade-off.

What the measured bill counts

  • Client egress on returned bytes.
  • Provider retrieval on bytes actually read from the provider.
  • Cross-region transfer on bytes that cross a private region pair.
  • API fees per admitted provider RPC. A ten-thumbnail search fan-out is ten reads, and retries are charged too.
  • Failed and partial transfers keep the bytes they really moved; a failure is not a free refund.

Index bytes are real bytes

A user-tag index is 352 B per image on every physical copy — about 528 GB per complete dataset, on top of the 12 TB of base records. It can still tip a store that was already close to capacity, especially with several copies. Fixing search by adding an index can therefore create a new capacity problem; that is a real trade-off, not a validation bug.

Cache capacity is a pool total. Per-instance share is capacityGb ÷ instances and must fit 22 GB for RAM or the declared SSD tier. Cache and metadata RAM are part of instance compute price and are never billed twice.

How to read the results

Find the right table

  1. Open Results & telemetry at the bottom of the workspace.
  2. Choose a case tab: Normal daily average, Peak daily average, One instance per pool, Link outage na-eu, or one of the three Region outage cases.
  3. Read Gates before the detailed numbers.
  4. Read Operations for Upload, Search and Detail.
  5. Then use the node Inspector and Memory and physical links to find where the time or bytes went.

Operation columns

Operations shows Offered, Completed, Success, Availability, Timely, Correct, p50, p95, p99, p99.9, Samples and Queue p95. The failure split and error codes are printed under each operation name.

  • Availability uses every offered request. Rejected, timed-out, incorrect, stale and missing-data responses are failures.
  • p50–p99.9 use successful responses only, and always show their sample count. Dropping traffic cannot improve a percentile.
  • p99.9 needs at least 10,000 successful samples per operation per case. A short run extends deterministically; an exhausted event or memory limit is incomplete, never a pass.

What a percentile means

Sort 10,000 successful requests from fastest to slowest. p50 is around the middle; p95 is around the 500th slowest; p99 is around the 100th slowest; p99.9 is around the 10th slowest. A p99.9 target is a promise about the tail, not about the average.

Average and peak are different questions

Average says how sustained the load was. Peak says how bad the worst instant was. A 100% peak by itself is not a failure: a brief spike can occur in a passing run. Look for errors, rejected and timed-out requests, high wait p95, and the latency tail. Conversely, a low average can hide a short saturation that only peak and p99.9 reveal.

The node Inspector

Select a node to see that case’s measured run metrics: CPU average / peak, RAM average / peak against the limit, IO average / peak, Network in / out peak against capacity, Queue average / peak · wait p95, Requests / errors / rejected, Timed out / healthy instances, and Bytes read / written. Metadata nodes also show shard and capacity load; caches show hit ratio, hits, misses and coalesced fills.

Memory and physical links

The Memory and physical links section shows RAM average, peak and limit per node, healthy instances, and every shared physical channel with capacity, average, peak, bytes sent and received, transfers and Queue p95. A logical edge on the canvas is not its own 100 Gbit/s link.

Experiments and saved state

A fair comparison

  1. Export the current graph if you may want it back.
  2. Keep the same Seed.
  3. Change exactly one setting or edge.
  4. Run again and open the same case tab.
  5. Compare Operations, then the relevant node and link rows.
  6. Keep the change only if the whole gate set improves.

What is saved

Nothing is saved automatically. Export saves the graph, node settings, positions and seed. Import opens that state later. A page reload or Reset starts from the starter graph and the default seed with no previous run. Open the help page in a new tab so your in-memory diagram is not replaced.

Things worth testing

  • Does the search failure disappear when only the index changes, and what does that do to metadata capacity?
  • Which queue grows first when you add load: app, metadata, provider endpoint, or a shared region link?
  • Does a cache improve a warm steady state but leave the cold start and upload path unchanged?
  • Does a third durable copy survive one instance loss where two cannot, and what does it cost?
  • Does a region outage fail because capacity is missing on the failover path, rather than because the arrow is missing?

The game shows reasons, not a hidden answer key. A change can be logically sensible and still lose on cost or on another case.

What the counters cannot tell you

The shared counters are useful, but they are not a distributed trace. Read them together.

  • Operation Queue p95 is not a total wait. It keeps the first non-zero queued wait for each request, not the sum of waits across every stage.
  • Node and link Queue p95 is shared waiting, not proof of cause. It aggregates tasks that used the same resource. It does not attribute a specific request’s delay to the exact resource that blocked it.
  • Do not add percentiles. p95 plus p95 is not the p95 of a pipeline. A p95 queue also cannot explain a p99.9 tail, because the rare event lies outside that 5% band.
  • There is no per-request waterfall view. The UI has no request trace or span waterfall. Use Operations, the node Inspector, the physical link table and the gates together.
  • Low CPU does not rule out a network or IO bottleneck. A request can wait on a NIC, disk IO, provider admission, metadata quorum, or head-of-line blocking while CPU looks idle.
  • The kernel is a fixed-lane FIFO model. It is not TCP and not ideal fair sharing. A wide multi-hop proxy path can wait behind another task’s head even when every resource has spare average capacity. This is a disclosed limitation, not a hidden penalty or bonus.

Don’t diagnose from one number

A high peak does not prove failure; a low average does not prove health. A successful p99.9 does not excuse failed availability. A missing error code does not prove the path was fast. Confirm the symptom in the same case, seed and window before changing the graph.

Optional model details

You do not need these coefficients to play. They are here when you want to know why the simulator produced a number.

Workload, targets and qualification
  • Local propagation is 1 ms one-way and the regional Client RTT is 20 ms. Inter-region one-way propagation is 40 ms for na–eu, 70 ms for eu–ap and 80 ms for na–ap. Each direction has its own 100 Gbit/s channel; the two directions are not pooled.
  • One million users, 50 uploads/day and 50 searches/day for 30 days: 1.5 billion images. Daily averages: 578.7 uploads/s, 578.7 searches/s, 1,157.4 detail clicks/s.
  • Each search returns ten 8 KB result records and ten 256 KB thumbnails. Upload carries one 4 MB original and 8 KB of metadata. Detail opens one 4 MB original and an 8 KB record.
  • Normal and peak targets are p99.9 successful responses: Detail 300 ms, Search 250 ms, Upload 1,000 ms. Incident targets: 600 ms, 800 ms and 2,000 ms. Availability is at least 99.5% in normal/peak and 98% in an incident. The final 10 s recovery window needs 99.5%.
  • Detail’s 300 ms target is a game adaptation of Google’s original 200 ms exercise. The game adds 1% recent-read probes across three regions and a 60 s remote-visibility window; a correct cross-region origin read would already spend about 227 ms before app, metadata and client overhead.
  • Seven required cases: Normal, Peak, One instance per pool, Link outage na-eu, and a separate Region outage for NA, EU and AP. A scenario subset is exploratory.
  • Each case: 20 s warm-up, 60 s measured traffic, up to 10 s request drain, then a separate no-new-offers consistency postlude through the last acknowledged upload + 120 s. Faults start at measured second 20, last 20 s, then 20 s recovery.
  • p99.9 requires at least 10,000 successful samples per operation per case. Availability uses every offered request; percentiles use successful responses only.
Work coefficients and resource kernel
  • CPU is core-milliseconds. An app request costs 0.25 ms parse plus 0.35/0.5/0.9 ms for detail/search/upload handling. Metadata point lookup is 0.2 ms; user index 0.35 ms; tag index 0.45 ms plus 200 posting reads.
  • Each instance has four IO lanes sharing 500 MB/s and 20,000 IOPS, so one lane is 125 MB/s and 5,000 IOPS. A stage lasts as long as its slowest of CPU, IO and network work.
  • One network flow owns one 1 Gbit/s lane on each physical resource of its explicit path. A 10 Gbit/s NIC exposes 10 one-way lanes in each direction; a 100 Gbit/s shared link or provider endpoint exposes 100 lanes per direction. Parallel arrows never add capacity.
  • Provider read service-start bands are 35/70/100/120 ms; write bands are 80/140/200 ms. A write acknowledgement follows the incoming payload and 4 ms of durable service.
  • Streaming reserves every hop together and pays one serialization. Buffered pays one serialization per hop and holds the payload. A relay uses a small share of CPU and IO, not a whole core per flow.
  • Propagation adds geographic delay and holds no bandwidth. A fault during propagation still loses the response, and bytes already serialized stay billed.
  • Search children are concurrent on the server side but share one end-user access stage. Coalesced fills make the second reader wait for the real fill; a failed fill wakes the waiter for a retry.
  • Metadata replication is direct per-origin, pipelined, and never rebroadcasts applied records. There is no general consensus, leader election or Byzantine protocol in v1. Every scenario starts with replicas caught up to the mature synthetic dataset.
  • Prices and coefficients are conditional in-game teaching values, not vendor quotes. The budget has been checked against two independent design families and five seeds in development, but it remains an in-game target, not a guarantee that any graph passes.
What the model deliberately simplifies
  • Metadata search is a bounded index-page work model, not a database implementation. “No index” means the model rejects search; it does not claim that a real SQL database cannot scan.
  • Transport is fixed-quantum lane reservation with one FIFO per resource, not TCP, congestion control or ideal fair sharing.
  • The provider’s replication is included in the fixed price and is not a player-owned copy. Its remote visibility is a teaching window, not a real vendor guarantee.
  • The node and link queue counters are shared-resource aggregates. They are not a causal per-request trace, and there is no waterfall view.
  • The UI labels are part of the product: use the exact names in this guide when comparing screenshots or notes.
